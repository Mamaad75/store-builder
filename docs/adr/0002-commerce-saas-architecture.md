# ADR 0002 — معماری هدف: فروشگاه‌ساز SaaS هم‌تراز میکسین، سازیتو و وپیدو

* **وضعیت:** پذیرفته‌شده (Accepted) — صاحب پروژه در 2026-11-20 تأیید کرد و فاز ۲.۱ شروع شد. قرارداد اجرایی لایه‌ها: `docs/architecture/modules.md`.
* **تاریخ:** 2026-11-20
* **پایه:** ADR 0001 (Next.js برای رابط کاربری، NestJS برای بک‌اند، Prisma + PostgreSQL) که در فاز ۱ پیاده شد.
* **هدف کسب‌وکار:** محصول SaaS فروشگاه‌ساز برای بازار ایران، با **حداقل ۱۰۰۰ فروشنده‌ی فعال** و قابل رشد بعد از آن.

---

## ۱. محصول: خط پایه‌ی بازار (از بررسی میکسین، سازیتو و وپیدو در 2026-11-20)

| دسته | آنچه **هر سه** دارند (حداقل لازم) | آنچه یکی یا دو تا دارند (تمایز) |
|---|---|---|
| ویترین | قالب آماده، دامنه‌ی اختصاصی، SSL | ویرایشگر بصری بخش‌ها (میکسین)، PWA (سازیتو)، طراحی اختصاصی |
| کاتالوگ | محصول فیزیکی، دسته‌بندی | تنوع محصول (رنگ/سایز)، انبار، محصول دانلودی، ورود از اکسل/اینستاگرام/باسلام |
| سفارش و پرداخت | مدیریت سفارش، درگاه **زرین‌پال** | ده‌ها درگاه مستقیم و واسط، **اقساطی** (اسنپ‌پی، ترب‌پی، دیجی‌پی)، کارت‌به‌کارت، کیف پول |
| ارسال | — | روش‌های ارسال دلخواه، هزینه بر اساس وزن، ارسال رایگان بالای مبلغ، الوپیک |
| بازاریابی | **ترب**، پیامک، سئوی خودکار | کد تخفیف، ایمالز، یادآوری سبد رهاشده با پیامک، وبلاگ، همکاری در فروش |
| مشتری | ثبت‌نام (اغلب با موبایل) | کیف پول، باشگاه مشتریان، هدیه‌ی تولد |
| عملیات | گزارش، دسترسی مدیر | نقش‌های کارکنان، اتصال به حسابداری، API باز، ربات تلگرام |
| قیمت | — | وپیدو: پلن رایگان دائمی و ۵۹۰ هزار تومان در ماه؛ میکسین: ۳٫۵ تا ۵٫۶ میلیون برای ۳ تا ۱۲ ماه؛ سازیتو: ۱۱ تا ۱۸۰ میلیون سالانه |

**نتیجه:** امروز محصول ما یک «سایت‌ساز کاتالوگ» است (بدون سبد، سفارش و پرداخت). برای رقابت، **هسته‌ی تجارت** (سبد، پرداخت، سفارش، ارسال،
مشتری با OTP) اولویت اول است؛ بعد ابزارهای رشد (تخفیف، ترب و ایمالز، دامنه‌ی اختصاصی، پیامک)؛ بعد کسب‌وکار پلتفرم (پلن و صورت‌حساب).

## ۲. اصول معماری (تصمیم‌ها)

### ۲.۱ «یکپارچه‌ی ماژولار» (Modular Monolith)، نه میکروسرویس
* بک‌اند یک برنامه‌ی NestJS می‌ماند که از **ماژول‌های مرزبندی‌شده (Bounded Context)** ساخته شده است. هر ماژول داده‌ی خودش را دارد و فقط از طریق
  رابط عمومی (`<context>.api.ts`) یا **رویداد دامنه** با ماژول دیگر حرف می‌زند؛ import مستقیم repository یا جدول ماژول دیگر با گارد معماری ممنوع است.
* **چرا:** ۱۰۰۰ فروشنده بار متوسطی است (بخش ۴). میکروسرویس هزینه‌ی عملیاتی، شبکه و ثبات داده را چند برابر می‌کند بدون سودی در این مقیاس. مرزهای
  تمیز امروز، جدا کردن یک ماژول (مثلاً پرداخت) را در آینده ممکن نگه می‌دارد.

### ۲.۲ لایه‌ها در هر ماژول (Clean Architecture)
```
modules/<context>/
  domain/          موجودیت‌ها، value objectها، قواعد و ماشین حالت؛ TypeScript خالص (بدون Nest، Prisma، HTTP)
  application/     use caseها (یک سرویس کاربردی برای ماژول کوچک؛ یک کلاس برای هر use case بزرگ)، portها (interface برای repository و سرویس بیرونی)، رویدادها
  infrastructure/  پیاده‌سازی portها: repository با Prisma، آداپتور درگاه پرداخت/پیامک/ارسال
  interface/       Controller، DTO (اسکیمای Zod مشترک)، Guard؛ فقط ورودی را اعتبارسنجی و use case را صدا می‌زند
  <context>.module.ts
```
* وابستگی همیشه به سمت داخل است: `interface → application → domain`؛ `infrastructure` portهای `application` را پیاده می‌کند. **گارد معماری** این را
  اجبار می‌کند (همان روش ۹۰+ گارد فعلی پروژه).
* منطق فعلی (فروشگاه، کاتالوگ، رسانه، صفحه‌ها، انتشار) به‌تدریج و فقط هنگام دست‌خوردن به این قالب درمی‌آید؛ بازنویسی یک‌جا نداریم.

### ۲.۴ چندمستأجری (Multi-tenancy) و جداسازی داده
* **یک پایگاه‌داده، یک schema، ستون `storeId` روی هر سطر مستأجر** (همان مدل فعلی). مالکیت در خود SQL چک می‌شود (repositoryهای owner-bound فعلی).
* **دفاع در عمق — Row-Level Security در PostgreSQL:** برای جدول‌های تجارت (سفارش، مشتری، پرداخت) سیاست RLS روی `current_setting('app.store_id')`
  که API در شروع هر تراکنش تنظیم می‌کند؛ کاربر پایگاه‌داده‌ی برنامه **مالک جدول‌ها نیست** (پس RLS را دور نمی‌زند). یک باگ در کوئری دیگر داده‌ی
  فروشگاه دیگر را نشان نمی‌دهد.
* شناسه‌ی فروشگاه همیشه از نشست احرازشده یا Host درخواست به‌دست می‌آید، **هرگز** از بدنه‌ی درخواست کاربر. آزمون‌های جداسازی مستأجر (فروشگاه A
  به داده‌ی B نمی‌رسد) برای هر endpoint جدید اجباری است.

### ۲.۵ دو جمعیت کاربر
* **فروشنده‌ها** (کاربران پلتفرم): نام کاربری و رمز (U1)، بعداً OTP؛ نقش در هر فروشگاه: مالک، مدیر، ویرایشگر کاتالوگ، پشتیبانی سفارش، حسابدار.
  مجوزها با Guard و policy در Nest بررسی می‌شوند، نه در رابط کاربری.
* **مشتری‌ها** (خریداران هر فروشگاه): فقط **موبایل + OTP**؛ هر مشتری متعلق به یک فروشگاه است (موبایل در هر فروشگاه یکتا). نشست مشتری روی
  میزبان همان فروشگاه و جدا از نشست فروشنده است.
* **OTP:** کد ۶ رقمی تصادفی امن، فقط hash آن ذخیره می‌شود، اعتبار ۲ دقیقه، حداکثر ۵ تلاش، محدودیت ارسال برای هر شماره و هر IP، پیام یکسان برای
  شماره‌ی ثبت‌شده و نشده.

### ۲.۶ پرداخت (پرریسک‌ترین بخش)
* `PaymentProvider` یک port است؛ آداپتورها: **زرین‌پال** (اول)، سپس PayPing/IDPay، اقساطی (اسنپ‌پی، ترب‌پی)، و اتصال مستقیم شاپرک در آینده.
* **قواعد ثابت:** مبلغ همیشه **عدد صحیح ریال** و از سفارش ذخیره‌شده خوانده می‌شود (هرگز از پارامتر بازگشت)؛ تأیید پرداخت فقط با فراخوانی
  `verify` سمت سرور؛ هر callback **idempotent** (کلید یکتا روی شناسه‌ی تراکنش)؛ ماشین حالت پرداخت (`initiated → pending → paid | failed | expired`)
  با انتقال‌های مجاز صریح؛ کار تطبیق (reconciliation) دوره‌ای برای پرداخت‌های بلاتکلیف.
* **کلیدهای درگاه هر فروشنده** رمزنگاری‌شده ذخیره می‌شوند (envelope encryption: کلید داده برای هر رکورد، کلید اصلی فقط از متغیر محیطی یا
  سرویس مدیریت رمز)؛ در لاگ، API و پنل هرگز به‌طور کامل نمایش داده نمی‌شوند.
* پول روی حساب پلتفرم نمی‌ماند: درگاه هر فروشنده به حساب خود او می‌ریزد (مدل «بدون کارمزد» رقبا و کم‌ریسک‌تر از نظر قانونی).

### ۲.۷ سفارش و موجودی
* ماشین حالت سفارش: `pending_payment → paid → processing → shipped → delivered`، شاخه‌های `cancelled` و `refunded`؛ هر انتقال در
  `OrderEvent` ثبت می‌شود (تاریخچه‌ی کامل).
* قیمت، نام و مشخصات هر قلم در لحظه‌ی سفارش **کپی** می‌شود (تغییر بعدی محصول، فاکتور قدیمی را عوض نمی‌کند).
* موجودی: کم کردن اتمی با شرط (`UPDATE ... SET stock = stock - n WHERE stock >= n`)؛ رزرو موقت هنگام شروع پرداخت و آزادسازی خودکار بعد از انقضا.
* شماره‌ی فاکتور: دنباله‌ی جداگانه برای هر فروشگاه، بدون فاصله.

### ۲.۸ کار ناهمگام: Redis + صف + Outbox
* **پیاده‌سازی (۲.۲a، 2026-11-20):** Valkey 8.1 به‌جای Redis (مجوز BSD، خودمیزبان)؛ جزئیات و وضعیت در `docs/async.md`.
* **Redis** (درون compose) برای: صف کارها (**BullMQ**)، rate limit (رابط `RateLimiter` فعلی آماده‌ی backend Redis است)، سبد مهمان، کلیدهای idempotency.
* **الگوی Outbox:** رویدادهای دامنه (مثلاً «سفارش پرداخت شد») در همان تراکنش پایگاه‌داده در جدول `outbox` نوشته می‌شوند و یک کارگر آن‌ها را به صف
  می‌فرستد؛ پس هیچ پیامک یا webhook از دست نمی‌رود و هیچ‌کدام برای تراکنش برگشت‌خورده فرستاده نمی‌شود.
* کارها: ارسال پیامک و ایمیل، فید ترب و ایمالز، پردازش تصویر، پاک‌سازی‌های فعلی، تطبیق پرداخت. scheduler فعلی به کارهای تکرارشونده‌ی BullMQ منتقل می‌شود.

### ۲.۹ API
* REST با پیشوند نسخه **`/api/v1`**، مستندات **OpenAPI** خودکار (برای اپ موبایل و API باز در آینده)، اسکیماهای Zod مشترک در `packages/shared`.
* خطاها با قالب ثابت (کد، پیام فارسی)، بدون stack؛ صفحه‌بندی cursor-based برای فهرست‌ها.
* سه سطح دسترسی جدا: `/api/v1/admin/*` (فروشنده)، `/api/v1/store/*` (مشتری روی میزبان فروشگاه)، `/api/v1/platform/*` (اپراتور پلتفرم).

### ۲.۱۰ ویترین و دامنه‌ی اختصاصی
* صفحه‌های فروشگاه همچنان از **نسخه‌ی منتشرشده‌ی تغییرناپذیر** ساخته می‌شوند (مزیت فعلی: انتشار، برگشت و کش امن). سبد و پرداخت تنها بخش‌های پویا هستند.
* کش: صفحه‌های منتشرشده با **برچسب نسخه** کش می‌شوند (CDN یا کش Caddy)؛ انتشار جدید فقط برچسب را عوض می‌کند (حل D13-11).
* دامنه‌ی اختصاصی: تأیید با رکورد TXT، سپس گواهی خودکار با **on-demand TLS** در Caddy که قبل از صدور از endpoint داخلی API می‌پرسد «این دامنه
  تأییدشده است؟» (جلوگیری از سوءاستفاده برای صدور گواهی دلخواه).

## ۳. امنیت (هدف: OWASP ASVS 5.0 سطح ۲؛ سطح ۳ برای پرداخت)
* همه‌ی کنترل‌های فعلی می‌مانند: CSP، HSTS، گارد Origin، rate limit، Argon2id، `authVersion`، لاگ بدون داده‌ی حساس، ممیزی وابستگی‌ها در CI.
* **جدید:** RLS (بخش ۲.۴)؛ رمزنگاری کلیدهای درگاه (۲.۶)؛ جدول **audit log** برای کارهای حساس (تغییر نقش، کلید درگاه، بازپرداخت، خروجی داده)؛
  webhookهای خروجی با امضای HMAC و **محافظت SSRF** (فقط https، رد IPهای داخلی)؛ اسکن رمز (secret scanning) و SAST در CI؛ آزمون‌های سوءاستفاده
  برای هر جریان پولی (دستکاری مبلغ، تکرار callback، رقابت دو پرداخت هم‌زمان).
* حریم خصوصی: کمینه‌سازی داده‌ی شخصی مشتری (نام، موبایل، آدرس)، دسترسی فقط برای نقش‌های مجاز، امکان خروجی و حذف به درخواست مشتری.

## ۴. ظرفیت برای ۱۰۰۰ فروشنده (برآورد، نه اندازه‌گیری)
* فرض: ۱۰۰۰ فروشگاه × میانگین ۲۰۰۰ بازدید در روز ≈ ۲ میلیون صفحه در روز ≈ **۲۵ درخواست در ثانیه** به‌طور میانگین، اوج حدود **۲۵۰**؛ بیشتر صفحه‌ها از کش.
  سفارش‌ها چند ده در دقیقه در اوج.
* **چیدمان پیشنهادی production:** ۲ نمونه‌ی web و ۲ نمونه‌ی api پشت Caddy (بدون حالت؛ نشست در کوکی)، PostgreSQL اختصاصی (۴ vCPU / ۱۶ GB) با
  **PgBouncer**، Redis، ذخیره‌سازی S3 + CDN. این با یک تا دو سرور قوی ممکن است.
* **پشتیبان‌گیری:** با ورود پول، `pg_dump` روزانه کافی نیست: **WAL archiving / PITR** (هدف از دست دادن داده کمتر از ۵ دقیقه) به‌اضافه‌ی dump روزانه.
* قبل از راه‌اندازی، **آزمون بار** (k6) روی staging با سناریوی مرور، سبد و پرداخت آزمایشی.

## ۵. کیفیت و نگه‌داشت‌پذیری
* هر ماژول جدید: آزمون واحد دامنه (بدون پایگاه‌داده)، آزمون use case با repository در حافظه، آزمون یکپارچه روی PostgreSQL واقعی (الگوی فعلی)،
  آزمون جداسازی مستأجر، و E2E برای جریان اصلی. آداپتورهای درگاه با **sandbox** خود درگاه آزموده می‌شوند.
* گاردهای معماری برای مرز ماژول‌ها و جهت لایه‌ها؛ TypeScript strict؛ قرارداد API با OpenAPI؛ هر تصمیم در `docs/decisions.md` و هر تغییر در CHANGELOG.
* مشاهده‌پذیری: لاگ ساخت‌یافته (موجود)، **متریک** (Prometheus روی شبکه‌ی داخلی)، ردیابی خطا (GlitchTip یا Sentry خودمیزبان)، هشدار بله (موجود).

| **۵ — رشد** | کد تخفیف؛ فید ترب و ایمالز؛ دامنه‌ی اختصاصی؛ یادآوری سبد رهاشده؛ درگاه‌های بیشتر و اقساطی؛ گزارش فروش | خط پایه‌ی رقابتی |
| **۶ — کسب‌وکار پلتفرم** | پلن و اشتراک، دوره‌ی آزمایشی، اعمال محدودیت پلن، پنل اپراتور | شرط فروش محصول |
| **۷ — راه‌اندازی** | production با PITR، پایش و برگشت‌پذیری؛ بتای محدود | — |
| بعد از آن | ویرایشگر کشیدنی، وبلاگ، PWA، API باز و webhook، اتصال حسابداری، کیف پول، امکانات هوش مصنوعی | تمایز، نه حداقل |

## ۷. تصمیم‌هایی که از شما لازم است (همه پیش از فاز ۳؛ هیچ‌کدام برای شروع فاز ۲ لازم نیست)
1. **سرویس پیامک** برای OTP و اطلاع‌رسانی (مثلاً کاوه‌نگار، SMS.ir، ملی‌پیامک).
2. **اولین درگاه پرداخت:** پیشنهاد زرین‌پال (در هر سه رقیب هست و sandbox دارد).
3. **مدل درآمد:** اشتراک ثابت (مثل میکسین و وپیدو) یا اشتراک + کارمزد؛ و آیا پلن رایگان دائمی (مثل وپیدو) داریم؟
