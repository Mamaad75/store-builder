# ADR 0001 — بک‌اند جدا با NestJS (روی Node.js و Express) و ورود با نام کاربری

* **وضعیت:** پیشنهادی (Proposed) — منتظر تأیید صاحب پروژه. هیچ کدی تغییر نکرده است.
* **تاریخ:** 2026-11-19
* **جایگزین می‌کند (پس از تأیید):** A-1 (یک برنامه‌ی Next.js)، A-2 (فقط Server Actions، بدون REST) و بخش «ایمیل» از A-3.

## زمینه
* درخواست صاحب پروژه: (۱) ثبت‌نام و ورود فعلاً با **نام کاربری + رمز** باشد (بعداً OTP)؛ (۲) بک‌اند یک **سرویس جدا روی Node.js با NestJS/Express و
  REST API** باشد تا خودش ساختار را بفهمد و نگه دارد.
* امروز بک‌اند هم Node.js است، ولی داخل Next.js: ۷ فایل Server Action (`src/app/**/actions*.ts`) ورودی‌ها را می‌گیرند و ماژول‌های دامنه را صدا می‌زنند.
* **یافته‌ی مهم:** منطق دامنه در `src/modules/*` (حدود ۵۳۰۰ خط: auth، stores، products، categories، media، pages، publishing، storefront، seo) تقریباً
  مستقل از Next.js است؛ فقط `auth/callbacks.ts` و `auth/session.ts` به `next-auth` وابسته‌اند. پس این کد **بازنویسی نمی‌شود، منتقل و دوباره استفاده می‌شود**.

## تصمیم پیشنهادی

### معماری هدف
```
مرورگر ──> Caddy ──┬── /api/*  ──> api  (NestJS روی Express، پورت 4000) ──> PostgreSQL، S3
                   └── بقیه    ──> web  (Next.js: داشبورد و نمایش فروشگاه‌ها) ── فقط از طریق HTTP به api
```
* **مخزن واحد (pnpm workspace):**
  * `apps/api`: NestJS. هر ماژول دامنه یک ماژول Nest می‌شود: Controller (مسیرهای REST) + Service (همان کد فعلی `src/modules`).
  * `apps/web`: Next.js فعلی، **بدون دسترسی مستقیم به پایگاه‌داده** (گارد معماری).
  * `packages/contracts`: اسکیماهای Zod مشترک (اعتبارسنجی ورودی در API و فرم‌ها در web) و نوع پاسخ‌ها.
* **یک مبدأ (same origin):** Caddy مسیر `/api/*` را به api و بقیه را به web می‌فرستد؛ در توسعه، Next همین کار را با rewrite انجام می‌دهد.
  نتیجه: کوکی‌ها first-party می‌مانند و CORS لازم نیست.
* **احراز هویت در API:** کوکی `httpOnly`، `Secure`، `SameSite=Lax` حاوی JWT امضاشده با همان `authVersion` امروز (بستن همه‌ی نشست‌ها با یک
  افزایش)، Argon2id و rate limit فعلی بدون تغییر. Auth.js حذف می‌شود.
* **CSRF:** Server Actions بررسی Origin را خودشان انجام می‌دادند؛ در REST این کار دستی است: گارد سراسری که برای هر درخواست تغییردهنده، `Origin`
  را با میزبان پلتفرم مقایسه می‌کند + `SameSite=Lax`.
* **امنیت لایه‌ی HTTP:** helmet، سقف اندازه‌ی بدنه (۶ MB برای آپلود)، اعتبارسنجی همه‌ی ورودی‌ها با همان Zod، پاسخ‌های خطای ثابت (بدون stack)،
  مالکیت در SQL مثل امروز (repositoryهای owner-bound بدون تغییر).
* **web:** Server Componentها با `fetch` به api (روی شبکه‌ی داخلی) و با کوکی کاربر داده می‌گیرند؛ فرم‌ها به API ارسال می‌شوند. صفحه‌های فروشگاه
  (زیردامنه‌ها) داده‌ی منتشرشده را از endpoint عمومی api می‌خوانند.
* **کارهای زمان‌بندی‌شده** (پاک‌سازی، scheduler، هشدار بله) به `apps/api` منتقل می‌شوند.

### ورود با نام کاربری (گام اول، در همین معماری فعلی)
* `User.username`: یکتا، ۳ تا ۳۰ کاراکتر از `a-z`، `0-9`، `_` و `.`، همیشه با حروف کوچک ذخیره می‌شود؛ نام‌های رزرو (admin، api، …) ممنوع.
* ثبت‌نام: نام، نام کاربری، رمز. ورود: نام کاربری + رمز. پیام خطای ورود همان پیام یکسان امروز (بدون لو دادن وجود حساب).
* **ایمیل:** اختیاری (تصمیم شما، بخش «پرسش‌ها»). بازیابی رمز با ایمیل فقط برای کسی ممکن است که ایمیل ثبت کرده؛ بعداً OTP جای آن را می‌گیرد.
* migration برگشت‌پذیر: ستون جدید `username`، پر کردن برای حساب‌های موجود در پایگاه‌داده‌ی توسعه، سپس `NOT NULL` و ایندکس یکتا؛ `email` اختیاری.

## گزینه‌های بررسی‌شده
| گزینه | چرا انتخاب نشد |
|---|---|
| ماندن روی Server Actions | با هدف صاحب پروژه (بک‌اند جدا و قابل‌فهم با Express/Nest) نمی‌خواند |
| REST با Route Handlerهای خود Next | ارزان‌تر، ولی بک‌اند جدا نمی‌شود و همان پیچیدگی Next باقی می‌ماند |
| Express خالی بدون Nest | آزادتر، ولی ساختار ماژول، تزریق وابستگی، گارد و pipe را باید خودمان بسازیم؛ Nest همین‌ها را استاندارد دارد و **زیرش Express است** |
| بازنویسی کامل منطق در Nest | پرخطر و پرهزینه؛ منطق فعلی آزموده و مستقل از فریم‌ورک است |

## پیامدها
* **مزیت:** بک‌اند مستقل و قابل‌فهم؛ API قابل استفاده برای اپ موبایل یا OTP در آینده؛ مرز روشن بین نمایش و منطق.
* **هزینه:** دو سرویس برای اجرا و پایش؛ یک رفت‌وبرگشت شبکه‌ی داخلی بیشتر؛ بازنویسی گارد امنیتی‌ای که Server Actions رایگان می‌دادند (CSRF)؛ بازنویسی
  گاردهای معماری و بخشی از آزمون‌های E2E؛ به‌روزرسانی Dockerfile، compose، Caddy و CI.
* **فاز ۱۴ (staging):** پیشنهاد می‌شود **بعد از** این مهاجرت انجام شود تا دو بار راه‌اندازی نشود؛ کارهای غیرکدی فاز ۱۴ (پرسش‌ها از پارس‌پک، خرید
  دامنه، ساخت بازوی بله) هم‌زمان پیش می‌روند.

## برنامه‌ی اجرا (هر مرحله: کد + آزمون + CI سبز + گزارش + تأیید شما)
| مرحله | محتوا | ریسک |
|---|---|---|
| U1 | **ورود با نام کاربری** در معماری فعلی (schema، migration، فرم‌ها، آزمون‌ها) | متوسط (migration) |
| N1 | تبدیل به مخزن چندبسته‌ای (`apps/web`، `packages/contracts`، جای `apps/api`)؛ **بدون تغییر رفتار** | متوسط (جابه‌جایی زیاد فایل) |
| N2 | اسکلت NestJS: پیکربندی و اعتبارسنجی env، لاگ ساخت‌یافته، Prisma، health/ready، helmet، گارد CSRF، Docker image، کار CI | کم |
| N3 | API احراز هویت (ثبت‌نام، ورود، خروج، من، تغییر رمز، خروج از همه‌جا، بازیابی) و جایگزینی Auth.js در web | **بالا** |
| N4 | API فروشگاه‌ها، دسته‌ها و محصولات؛ داشبورد به API وصل شود | متوسط |
| N5 | API رسانه (آپلود)، صفحه‌ها، ظاهر و تغییر قالب | متوسط |
| N6 | API انتشار، زیردامنه، خواندن عمومی فروشگاه، SEO؛ صفحه‌های فروشگاه از API بخوانند | بالا |
| N7 | حذف Server Actions و Auth.js؛ گاردهای معماری جدید (web به DB دسترسی ندارد)؛ scheduler در api؛ compose، Caddy، runbook | متوسط |

## پرسش‌های باز (تصمیم صاحب پروژه)
1. ایمیل در ثبت‌نام **اختیاری** بماند (برای بازیابی رمز تا قبل از OTP) یا کاملاً حذف شود؟
2. ترتیب پیشنهادی: اول U1 (نیاز فوری)، سپس N1 تا N7، سپس فاز ۱۴. موافقید؟
