# چک‌لیست خرید و پیکربندی فاز ۱۴ (Staging)

این سند نقطه‌ی شروع فاز ۱۴ است (طبق `docs/roadmap.md` و `docs/decisions.md`، بخش «Deployment restrictions»).
**هیچ چیزی بر اساس این سند خریده، وصل یا deploy نمی‌شود.** هر مرحله‌ای که هزینه دارد، به حساب بیرونی وصل می‌شود یا روی سرور اجرا می‌شود، تأیید صریح جداگانه‌ی صاحب پروژه را لازم دارد.

وضعیت: **پیش‌نویس، منتظر تصمیم‌های بخش ۱**. تاریخ: 2026-11-18.

قواعدی که در کل فاز ۱۴ ثابت‌اند:
* رمزها، توکن‌ها و کلیدها هیچ‌وقت در چت، git، CI یا image نمی‌آیند؛ فقط در `.env.production` روی سرور (mode 600) و کنسول سرویس‌دهنده.
* دسترسی به سرور فقط با یک کاربر deploy جدا و کلید SSH محدود؛ کلید خصوصی هیچ‌وقت در چت نمی‌آید.
* staging و production دو محیط جدا هستند (سرور، پایگاه‌داده، bucket، کلید و `AUTH_SECRET` جدا).

## ۲. الزامات فنی هر مورد (معیار انتخاب)

### ۲.۱ محل میزبانی (T1)
* **ایران:** تأخیر کمتر برای کاربر ایرانی، پرداخت ریالی، احتمال دسترسی‌پذیری بهتر در زمان اختلال اینترنت بین‌الملل. باید بررسی شود: SLA، snapshot، امکان IPv4 ثابت و پشتیبانی Docker.
* **خارج:** سرویس‌های جاافتاده‌تر، ولی پرداخت، تحریم و دسترسی‌پذیری از ایران ریسک دارد.
* **یافته‌ی اندازه‌گیری‌شده (2026-11-18، از شبکه‌ی توسعه‌دهنده، نه از یک سرور):** Docker Hub (`registry-1.docker.io`، `auth.docker.io`) پاسخ **403** داد (تحریم)؛ `ghcr.io`، `registry.npmjs.org`، `proxy.golang.org`، GitHub و Let's Encrypt در دسترس بودند. اگر سرور در ایران باشد، pull و build ایمیج‌های پایه از Docker Hub مستقیم کار نمی‌کند: یا mirror سرویس‌دهنده، یا ساخت ایمیج در CI و pull از `ghcr.io` (اثر روی T10 و D13-10). **قبل از خرید، همین آزمون روی یک سرور آزمایشی ساعتی تکرار شود.**
* در قطعی اینترنت بین‌الملل، تمدید گواهی (Let's Encrypt) و دسترسی به registryها از سرور داخلی قطع می‌شود؛ گواهی ۹۰ روزه است و Caddy حدود ۳۰ روز مانده به انقضا تمدید می‌کند، پس حاشیه‌ی تحمل حدود یک ماه است.
* سرور، storage و DNS بهتر است در یک خانواده باشند تا مسیر شبکه و قرارداد ساده بماند؛ **backup بیرون از سرور باید جای دیگری باشد** (T7).

### ۲.۲ سرویس DNS (T3)
* برای گواهی wildcard (`*.<دامنه>`) Caddy به چالش ACME DNS-01 و ماژول سرویس‌دهنده‌ی DNS نیاز دارد (D13-7، I-2).
* ماژول‌هایی که در سازمان `caddy-dns` وجود دارند و فعال‌اند (بررسی‌شده با GitHub API در 2026-11-18):

| ماژول | آخرین تغییر | مجوز |
|---|---|---|
| `github.com/caddy-dns/arvancloud` | 2026-02 | MIT |
| `github.com/caddy-dns/liara` | 2026-08 | MIT |
| `github.com/caddy-dns/parspack` | 2026-08 | MIT |
| `github.com/caddy-dns/cloudflare` | 2026-03 | Apache-2.0 |
| `github.com/caddy-dns/hetzner` | 2026-05 | MIT |

* ماژول‌های ایرانی کاربران کمی دارند: **قبل از انتخاب، کد ماژول بازبینی و روی staging آزموده می‌شود** (صدور و تمدید گواهی).
* الزامات: توکن API با کمترین دسترسی (فقط ویرایش رکوردهای همین zone)، رکوردهای `A` برای `<دامنه>`، `www` و `*`.

### ۲.۳ سرور (T4)
| | staging | production (فاز ۱۵، برای برآورد) |
|---|---|---|
| CPU / RAM | ۲ vCPU / ۴ GB (ساخت image با `next build` روی سرور حافظه‌ی زیادی می‌خواهد) | ۴ vCPU / ۸ GB |
| دیسک | ۴۰ GB+ SSD | ۸۰ GB+ SSD |
| سیستم‌عامل | Ubuntu 24.04 LTS یا Debian 12 | همان |
| لازم | IPv4 ثابت، Docker Engine + Compose v2، فایروال (فقط ۲۲، ۸۰، ۴۴۳)، snapshot | همان + snapshot خودکار |

### ۲.۴ Object storage (T5)
باید همه‌ی این‌ها را داشته باشد (آزمون‌های storage همین‌ها را بررسی می‌کنند و نباید ضعیف شوند):
* API سازگار با S3: `PutObject`، `DeleteObject`، `ListObjectsV2` (readiness و cleanup).
* **bucket policy واقعی:** خواندن ناشناس فقط `GetObject`؛ `List`، `Put` و `Delete` ناشناس باید ۴۰۳ بگیرند.
* کلید دسترسی محدود به همین bucket.
* آدرس عمومی پایدار برای `S3_PUBLIC_BASE_URL` (در CSP به‌عنوان تنها مبدأ خارجی تصویر می‌آید).
* versioning یا replication برای backup تصاویر (دیتابیس فقط کلید تصاویر را نگه می‌دارد).

### ۲.۵ ایمیل (T6)
* SMTP یا HTTP API؛ امکان تأیید دامنه‌ی فرستنده با SPF، DKIM و DMARC.
* تحویل به Gmail و Outlook در staging آزموده شود (لینک بازیابی رمز سرتاسر).
* **کار کد لازم دارد** (بخش ۳): امروز فقط transportهای `none`، `log` و `file` وجود دارد.

### ۲.۶ Backup بیرون از سرور (T7)
* مقصد جدا از سرور و ترجیحاً از سرویس‌دهنده‌ی دیگر؛ کلید فقط با دسترسی نوشتن (بدون حذف) در صورت امکان.
* برنامه‌ی زمانی (پیشنهاد: روزانه)، نگه‌داری ۱۴ روز (`RETENTION_DAYS`)، هشدار در صورت خروج غیرصفر یا نبودن فایل جدیدتر از ۲۶ ساعت (`docs/runbook.md`).

### ۲.۷ لاگ و هشدار (T8، T9)
باید این رخدادها هشدار بدهند (roadmap، D10-13 و فاز ۱۳):
`job.failed`، `scheduler.unhealthy`، `startup.refused`، `readiness.failed`، `media.release_failed`، `media.reclaim_failed`، `backup.failed`، و **نبودِ اجرای موفق** در بازه‌ی مورد انتظار، و `scanTruncated: true` در دو اجرای پشت‌سرهم.
به‌علاوه یک مانیتور uptime بیرونی روی `https://<دامنه>/api/ready`.

## ۵. ترتیب اجرای staging (هر «⛔» یعنی توقف و تأیید صریح شما)

1. ⛔ تصمیم‌های T1 تا T10 و تأیید هزینه‌ها (بخش ۶).
2. ⛔ خرید/ساخت حساب‌ها توسط خود شما (دامنه، DNS، سرور، storage، ایمیل، مقصد backup). رمزها نزد شما می‌مانند.
3. آماده‌سازی سرور: کاربر deploy، کلید SSH محدود، فایروال، به‌روزرسانی‌ها، Docker.
4. رکوردهای DNS و ساخت توکن DNS با کمترین دسترسی.
5. ساخت bucket، policy و کلید محدود؛ **اجرای آزمون‌های storage علیه آن** (ناشناس: List/Put/Delete = ۴۰۳).
6. کارهای K1 و K2 (کد، بازبینی، CI سبز).
7. ⛔ اولین deploy روی staging طبق `docs/runbook.md` (backup قبل از هر deploy).
8. بررسی: `/api/ready` = ready، سلامت سرویس‌ها، گواهی wildcard برای یک فروشگاه آزمایشی، یک چرخه‌ی کامل ثبت‌نام → فروشگاه → محصول → انتشار → زیردامنه.
9. ایمیل: بازیابی رمز سرتاسر با صندوق واقعی.
10. **دروازه‌ی D10-13:** تزریق خطا (رد حذف در object store یا نگه‌داشتن قفل فروشگاه)، اطمینان از خروج غیرصفر و رسیدن هشدار، رفع خطا، اطمینان از پاک شدن باقی‌مانده‌ها در اجرای بعدی (`failures: 0`) و اینکه اجرای بعدی چیزی تغییر نمی‌دهد. **اجرای زمان‌بندی‌شده، نه فقط دستی.**
11. backup بیرون از سرور + **مانور بازیابی روی سرور واقعی** و ثبت زمان بازیابی.
12. ثبت نتایج در یک گزارش انتشار فاز ۱۴.

## ۸. بررسی سرویس‌دهنده‌ها (2026-11-18، از روی مستندات رسمی؛ هیچ حسابی ساخته نشده)

### لیارا (liara.ir): هر چهار سرویس در یک‌جا
| سرویس | آنچه مستندات می‌گوید | با الزامات ما |
|---|---|---|
| ایمیل (`docs.liara.ir/email-server/`) | ارسال تراکنشی (مثال خود مستندات: بازیابی رمز)؛ SMTP روی **587 با STARTTLS** و **465 با TLS**؛ رکوردهای SPF، DKIM، MX و صفحه‌ی DMARC | ✅ دقیقاً با transport ما (DM2-1) جور است |
| ذخیره‌سازی (`docs.liara.ir/object-storage/`) | «سازگاری کامل با S3» و AWS SDK؛ کلید دسترسی؛ اتصال دامنه به باکت؛ سطح دسترسی باکت فقط **عمومی یا خصوصی** | ⚠️ مستندات نمی‌گوید در حالت «عمومی» فهرست‌گرفتن (LIST) یا نوشتن ناشناس بسته است، و از bucket policy حرفی نمی‌زند. الزام ما (فقط GET ناشناس) **باید با آزمون‌های storage روی یک باکت آزمایشی ثابت شود** (`STORAGE_TEST_ENFORCES_POLICY=1`)؛ اگر LIST باز باشد، این سرویس برای تصاویر پذیرفتنی نیست |
| DNS (`docs.liara.ir/dns-management-system/`) | مدیریت رکورد؛ ماژول Caddy (`caddy-dns/liara`) با **کلید API کنسول** کار می‌کند | ⚠️ کلید API به‌احتمال زیاد به کل حساب دسترسی دارد، نه فقط به رکوردهای DNS (خلاف اصل کمترین دسترسی). باید بررسی شود که کلید محدود ممکن است یا نه؛ اگر نه، ریسک ثبت و پذیرفته شود یا DNS جای دیگری باشد |
| سرور (`docs.liara.ir/iaas/`) | سرور مجازی ابری (IaaS) | باید آزمون بخش ۲.۱ (mirror داکر، ghcr.io، Let's Encrypt) روی خود سرور اجرا شود |

### آروان‌کلاد (arvancloud.ir)
* ماژول Caddy (`caddy-dns/arvancloud`) با کلید API کار می‌کند؛ mirror داکر آروان (`docker.arvancloud.ir`) از شبکه‌ی ما کار کرد.
* منابع جانبی نشان می‌دهند API ذخیره‌سازی آروان عملیات bucket policy دارد، ولی **مستندات رسمی خوانده نشد** (سایت مستندات از بیرون باز نشد). باید مستقیم بررسی شود.

### پیشنهاد (منتظر تصمیم شما)
* **اصلی:** لیارا برای سرور، ایمیل و (اگر آزمون باکت قبول شد) ذخیره‌سازی؛ DNS بسته به نتیجه‌ی بررسی کلید API.
* **پشتیبان بیرون از سرور (T7):** باکت در **سرویس‌دهنده‌ی دیگر** (مثلاً آروان‌کلاد)، تا خرابی یا قطع یک حساب، backup را هم نبرد.
* **قبل از هر خرید ماهانه:** یک سرور ساعتی و یک باکت آزمایشی، و اجرای دو آزمون: (۱) دسترسی سرور به mirror، `ghcr.io` و Let's Encrypt؛
  (۲) آزمون‌های امنیتی storage روی باکت. ساخت حساب و پرداخت با خود شماست.

## ۹. تصمیم‌های شما (2026-11-18) و بررسی پارس‌پک

| # | تصمیم | وضعیت |
|---|---|---|
| T2 | دامنه‌ی **`.ir`** (خرید از طریق پارس‌پک ممکن است) | ✅ تصمیم گرفته شد؛ خرید با شما |
| T3–T6 | **پارس‌پک** برای سرور، DNS، ذخیره‌سازی و ایمیل | ✅ تصمیم گرفته شد، با ۴ مورد تأییدنشده (پایین) |
| T7 | backup بیرون از سرور نزد **همان سرویس‌دهنده** | ✅ تصمیم شما؛ **ریسک پذیرفته‌شده:** مشکل یا تعلیق حساب پارس‌پک، سرور و backup را با هم می‌برد |
| T9 | هشدار از طریق **بله** (به‌جای تلگرام) | ✅ تصمیم گرفته شد (D14-3). `api.telegram.org` از ایران در دسترس نیست؛ API بازوی بله (`tapi.bale.ai`) از شبکه‌ی ایران پاسخ داد |

**آنچه مستندات پارس‌پک تأیید می‌کند (`docs.parspack.com`):** ثبت دامنه‌ی `.ir`؛ مدیریت DNS در پنل CDN (رکوردهای A، CNAME، MX، TXT، SRV، CAA و DNSSEC)؛
فضای ابری با «پروتکل S3» و AWS SDK، باکت پیش‌فرض خصوصی با حالت عمومی/خصوصی، اتصال دامنه و SSL؛ ایمیل سازمانی با سرویس SMTP IP
(تا ۲۰۰۰ ایمیل در روز با IP اختصاصی؛ SPF را پشتیبانی تنظیم می‌کند)؛ سرور ابری. ماژول Caddy `caddy-dns/parspack` با توکن API وجود دارد.

**چهار مورد که باید پیش از خرید ماهانه از پشتیبانی پارس‌پک پرسیده یا آزموده شود:**
1. **باکت عمومی:** آیا فقط خواندن فایل ناشناس آزاد است و فهرست‌گرفتن، آپلود و حذف ناشناس ۴۰۳ می‌گیرند؟ (با آزمون‌های storage ما روی یک باکت آزمایشی ثابت شود.)
2. **DNS:** رکورد wildcard (`*`) پشتیبانی می‌شود؟ توکن API را می‌شود فقط به DNS همین دامنه محدود کرد؟
3. **ایمیل:** آدرس سرور SMTP و درگاه‌ها؛ **TLS یا STARTTLS اجباری** (transport ما بدون رمزنگاری ارسال نمی‌کند)؛ امضای DKIM و DMARC برای دامنه‌ی ما.
4. **سرور:** دسترسی به mirror داکر (آروان یا mirror خود پارس‌پک)، `ghcr.io` و Let's Encrypt از روی سرور.
